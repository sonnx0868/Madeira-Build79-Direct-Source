# Abrupt guest exit terminates the iOS host

The15:03:20 BeamNG0.34 content test passed all133 mounts and the exact111-byte Grid file read. The user then confirmed Madeira returned to Home Screen. Runtime958b2b91ff86d85f records renderer PID0194/main thread0198 calling NtTerminateProcess(current-process pseudo-handle, exit_code0), followed by termination of its worker threads. It does not show a preceding graceful handle0 exit request for that renderer. No matching new native fault report was obtained; a newly copied CPU resource report names a different app bundle path and records action taken:none, so it is not evidence of this exit.

The installed native binary607600… contains a concrete porting defect. In NtTerminateProcess, after a successful self-termination server reply and a nonnull handle, process_exiting==0 calls abort_process. At nativeVA0x1001255f8 abort_process calls the Darwin `_exit` import directly. That terminates the whole iOS host. The usual exit_process path instead calls the existing process_exit_wrapper: it resolves the current guest PEB, closes that guest's server connection, releases its fd cache/JIT allocation, and enters wine_ios_exit to end the guest execution thread. This explains why an abrupt child exit can behave differently from the working graceful CPU/TLS diagnostic exit.

The test package redirects only the BL at0x1000efd98 from abort_process0x1001255e4 to the existing exit_process0x100125814. Its four-byte instruction changes13d60094→9fd60094 (one byte actually differs). The request to the Wine server, self test, null-handle behavior, other-process termination, already-exiting path and status argument remain untouched. This is scoped to the iOS native binary. Conventional Unix Wine's host-per-guest behavior must not be changed globally.

Semantic source equivalent for the iOS port only: once NtTerminateProcess has a successful self reply and a nonnull handle, call its existing exit_process(exit_code) for both values of its per-guest process_exiting flag. It must remain non-returning and retain the preceding server request. No general redirection of abort_process callers or Darwin `_exit` imports is proposed.

build.py verifies the exact v3 IPA and native hashes, the single-arm64 FAT wrapper, the original guard and adjacent normal-exit instructions. The patch uses no code cave or new runtime allocation. It changes only Payload/Madeira.app/Madeira; every other member is compared byte-for-byte. Signing is performed by the existing installer after the change.

test_branch.py executes the actual before/after native instructions in Unicorn:1024 cases across both binaries,4 existing-exit flag values,8 status values and16 condition-flag combinations. It checks destination, status, return address, other registers, stack and state memory. Original abrupt cases reach abort_process; patched ones reach exit_process; existing normal cases remain identical. This does not execute the complete cleanup body or prove iPad behavior.

GuestExit.c provides the physical regression test. A small parent launches four copies of itself: graceful exit0, abrupt self-termination0, abrupt19 and abrupt0xc0000005. The last is an exit code, not an induced access violation. Each child must signal completion and preserve its exact Windows exit status; the parent writes a durable log after every case and must reach the final PASS. It does not launch a game, modify settings, or terminate any process it did not create. A timeout reports failure and leaves the child untouched. All four cases passed in an isolated Linux Wine prefix; on iPad, the user confirmed Wine Desktop survived. The physical log passed graceful exit0 but reported exit1 for abrupt exit0; the remaining cases did not run. The runtime traced that mismatch to the separate fd+1 decoding defect in ios_fd_cache_release, now addressed by the v2 correction.

This correction addresses host survival during guest termination. It neither proves nor fixes the original reason CEF chooses to exit. The previous async-cancellation lifetime proposal is separate and remains uninstalled. Existing cleanup may expose another issue when it is exercised by abrupt exits; the small test is required before interpreting a further BeamNG run.
